## 結論: 今回は見送りました

GitWand という「**マージコンフリクトの 95% を自動解決する**」Git クライアントを試しました。**結論から書くと、今回は導入を見送りました。**

- 公式サイト: <https://gitwand.app/>
- リポジトリ: <https://github.com/devlint/GitWand>(MIT)
- CLI: <https://www.npmjs.com/package/@gitwand/cli>

前提として、**GitWand はまだ生まれて間もないプロジェクト**です。

- リポジトリができたのが 2026-04-03、npm の初版公開が 2026-04-20
- そこから約 3 か月で 39 回リリースされ、現在 v3.6.0(2026-08-02 時点、★154、MIT)

4 か月で 39 リリースという速度で作られている最中のツールです。以下に書く引っかかりは欠陥リストというより、その途中経過を今この時点で覗いた記録だと思って読んでください。

見送った理由を 1 行にすると、こうなります。

> **自動解決の能力を引き出すための設定が、そのまま「壊れたファイルを黙って通す」設定でもあった**

既定の git 設定のままだと、GitWand は自分が持つ分類パターン 10 個のうち 4 個を使えません(実測で 7 件中 3 件しか解けませんでした)。使えるようにするには `merge.conflictStyle` を `diff3` 系にする必要があるのですが、**そうすると今度は、GitWand 自身が「手動解決が必要」と判定したハンクに union を適用して `✓ resolved` と報告してきます**。私の手元では、`actions/checkout` が 2 回並んだ GitHub Actions の設定ファイルが生成されました。YAML としては valid なので、構文チェックもコンフリクトマーカー検査もすり抜けます。

安全側の設定では旨みが薄く、旨みのある設定では黙って壊れる。この二択になった時点で、v3.6.0 の今は自分の作業に入れないと判断しました。裏を返せば、ここが片付けば残りは十分に魅力的です。

ただ、エンジン本体で困った場面はありませんでした。絶対に自動で触られたくない箇所として仕込んだ「両ブランチが別アルゴリズムで書き直した関数」には手を出さず、自動解決された分は型チェックも通っています。惜しい、というのが正直なところなので、何が良くて何で詰まったのかを検証手順ごと書き残します。

### 何に期待して試したのか

トップページにはこう書いてあります。

> 8 deterministic patterns — zero gambling with your code
> 0 hallucinations — fully deterministic

「あなたのコードでギャンブルはしない」「ハルシネーションはゼロ、完全に決定論的」。マージコンフリクトの trivial な部分を自動で片付けて、人間は本当に難しいマージだけ見ればいい、という思想です。MIT ライセンス、完全無料、Rust + Tauri 2 製、テレメトリなし、アカウント登録も不要。

思想はすごく好みです。コンフリクト解消の大半はどう考えても機械の仕事で、あれを人間が毎回目で追っているのは無駄だと思っているので。

ただ「95%」も「ギャンブルしない」も、触ってみないと本当かどうか分かりません。なので検証用の TypeScript プロジェクトを作り、分類器を 1 つずつ狙い撃ちするコンフリクトをわざと仕込んで、CLI・デスクトップアプリ・MCP サーバの 3 面から踏ませてみました。

検証環境は macOS 26.4.1 (Apple Silicon)、GitWand **v3.6.0**、git 2.50.1、Node.js v26 です。

## GitWand はどういうツールか

コンフリクト解消に全振りした Git クライアント、という感じのツールです。

- **コンフリクトエンジン**: 決定論的なパターンで自動解決。信頼度スコアと decision trace 付き
- **3 つの窓口**: デスクトップアプリ / CLI (`@gitwand/cli`) / VS Code 拡張
- **MCP サーバ**: Claude Code や Cursor から AI エージェント経由で叩ける
- **おまけ**: コミットグラフ、PR 管理、worktree 管理、シークレットスキャン
- **ローカル完結**: LLM フォールバックは opt-in。既定ではコードは外に出ない

「AI がなんとなくマージしてくれる」系ではなく、まず決定論的に解ける分を解いて、残りを人間か LLM に回す設計になっています。この順番なら自分の手が要る箇所だけが残るはずで、そこに期待して触りはじめました。

## インストール

CLI は npm です。

```bash
npm install -g @gitwand/cli
gitwand --help
```

デスクトップは GitHub Releases から `.dmg` を落とすだけ。開く前に署名を確認しました。

```console
$ codesign -dv --verbose=2 /Volumes/GitWand/GitWand.app

$ spctl -a -vvv -t exec /Volumes/GitWand/GitWand.app
```

Developer ID 署名 + notarization 済みなので、「開発元を検証できません」の壁を殴る作業は発生しませんでした。ダブルクリックしてそのまま起動できています。

Tauri 製で、起動は体感一瞬でした。Electron 製の Git クライアントを触ったあとだと、この軽さははっきり分かります。

### どのパターンを狙ったのか

この 2 つを突き合わせると、こうなります。

| ファイル | main (ours) | feature (theirs) | 狙ったパターン |
|---|---|---|---|
| `package.json` | version 1.3.0 / zod 追加 | version 1.2.1 / zod + nanoid 追加 | `value_only_change` + 片側追加 |
| `src/config.ts` | `timeoutMs` を追加 | `retries` を追加 | `non_overlapping` |
| `src/index.ts` | import をアルファベット順に | import をグループ順に | `reorder_only` |
| `src/utils.ts` | 4 スペース整形 + 関数削除 | タブ整形 + 関数維持 | `whitespace_only` / `delete_no_change` |
| `README.md` | 箇条書きを 1 行追記 | 別の 1 行を追記 | `insertion_at_boundary` |
| `.github/workflows/ci.yml` | `checkout@v5` に更新 | `checkout@v4.2.2` に固定 | `value_only_change` |
| `src/rate-limit.ts` | トークンバケット実装 | スライディングウィンドウ実装 | **解けないはずの本物** |

最後の `rate-limit.ts` が重要です。同じ関数を、両ブランチが完全に別のアルゴリズムで書き直しています。これは人間が意思決定するしかないやつで、ここを機械が勝手にマージしてくるようなら信用できない。今回の合否はここで決めることにしました。

この構成を作る `setup-lab.sh` は付録に全文を置いてあります。手元で同じ状態を再現したい場合はそちらを。

## マージ前に予測する: `gitwand preview`

GitWand にはマージする前に衝突を予測する機能があります。ワーキングツリーも index も HEAD も触らないので副作用はありません。

```console
$ gitwand preview --branch=feature/api-v2

Merge: feature/api-v2
Risk: HIGH

  .github/workflows/ci.yml — 0/1 auto-resolvable (0%)
  README.md — 0/1 auto-resolvable (0%)
  package.json — 0/2 auto-resolvable (0%)
  src/config.ts — 0/0 auto-resolvable (100%)
  src/index.ts — 0/1 auto-resolvable (0%)
  src/rate-limit.ts — 0/1 auto-resolvable (0%)
  src/utils.ts — 0/1 auto-resolvable (0%)

  Total: 0/7 conflicts auto-resolvable
```

7 件中 0 件しか自動解決できない、リスク HIGH。マージ前にこれが分かるのは良くて、「今日はやめとくか」の判断材料になります。

……のですが、この件数はマージ後の実測とは一致しませんでした。同じリポジトリで実際に `git merge` してから `gitwand resolve` を走らせると、7 件中 3 件が自動で解けます。

| 何を見たか | 自動解決できると言った数 |
|---|---|
| `gitwand preview`(マージ前) | **0 / 7** |
| `gitwand status`(マージ後) | 3 / 7 |
| `gitwand resolve` の実測 | **3 / 7** |

`preview` はワーキングツリーを一切汚さない代わりに、実際のコンフリクトマーカーが存在しない状態でシミュレーションしています。そのぶん判定に使える情報が少なく、悲観側に倒れているようです(内部実装までは追っていないので、ここは推測です)。

自分の使い方としては、`preview` は `Risk: HIGH / MEDIUM / LOW` を見るところまでにしました。件数を真に受けて「0 件なら全部手作業か」と構えると、実際には機械に任せられる分まで手で潰すことになります。「重いマージが来ている」というアラートとしては十分に働いてくれたので、その用途では引き続き使えそうです。

あと `src/config.ts — 0/0 auto-resolvable (100%)` の表示、0 件中 0 件で 100% は落ち着かないです。


次に `--dry-run --verbose` を付けてみます。書き込む前に判断根拠を全部見せてくれるので、いきなりファイルを書き換えられる不安なしに試せました。

ひとつ補足すると、この説明文はフランス語で出力されます。ロケールを英語に上書きしても変わりませんでした。

```console
$ LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 LANGUAGE=en gitwand resolve --dry-run --verbose
    L3 [value_only_change] auto — Même structure avec 1 valeur volatile différente...
```

英語と綴りが近い語が多いので(`Conflit complexe` = complex conflict)、雰囲気は追えます。ただ自分は仏語を読めないので、trace を根拠に判断したい場面では、その都度訳しながら読むことになりました。i18n はまだ英語まで手が回っていない段階なのだと思います。

```console
$ gitwand resolve
```

| `src/utils.ts` | `insertion_at_boundary` | **手動** | ✅ union したら壊れていた |
| `src/rate-limit.ts` | `complex` | **手動** | ✅ **触らずに残した** |

`rate-limit.ts` に手を出さなかったのが、触っていて一番安心したところです。自分で選ぶべき箇所が、選べる形のまま残っていました。

`package.json` の version が 1.3.0(高い方)になったのも、自分が手でやる場合と同じ選択でした。ただし説明文には `résolution : accepter theirs`(theirs を採用)と書いてあります。theirs は 1.2.1 なので、文字通りならバージョンのダウングレードです。実際に書き込まれたのは 1.3.0 なので、**trace の文言と実際の動作がズレています**。`index.ts` の import 順も同様で、trace は「theirs の順を採用」と言いながら結果は ours の順でした。

結果は期待どおりなのに、説明を読むと逆のことが書いてある。trace を読んで判断しようとしていたので、ここで一度手が止まりました。

残り 4 件は自分で解いて、型チェックまで通しました。

```console
$ npm run typecheck
$ echo $?
0
```

自動解決された 3 件は 1 つも壊れていませんでした。任せた部分を後から手で直す羽目にはなっていません。

## decision trace を読む — エンジンは実は 12 段構え

MCP サーバの `gitwand_explain_hunk` を叩くと、分類器が何を試して何故落ちたかが全部出てきます。ここが読んでいて一番面白い部分でした。

`rate-limit.ts` の trace です(説明は訳しています)。

```
type: complex | hasBase: false | confidence: 60 medium

 - same_change: false             | 両ブランチの内容が異なる
 - delete_no_change: false        | diff2 では ours も theirs も空でない
 - one_side_change: false         | Base (diff3) 未提供 — diff3 が必要なためスキップ
 - non_overlapping: false         | Base (diff3) 未提供 — diff3 が必要なためスキップ
 - whitespace_only: false         | trim 正規化しても差が残る
 - reorder_only: false            | 単純な並べ替えではない
 - insertion_at_boundary: false   | 片側にしかない行が非対称に存在
 - value_only_change: false       | 行数が違う — 構造が異なる
 - token_level_merge: false       | Base (diff3) 未提供 — スキップ
 - refactoring_aware_merge: false | Base (diff3) 未提供 — スキップ
 - llm_proposed: false            | LLM フォールバック無効
 - complex: true                  | 自動パターンなし — 手動解決が必要
```

まず、公称の「8 パターン」より多いです。`token_level_merge` と `refactoring_aware_merge` という上位パターンが実装されていて、実際の分類ステップは 12 段(実パターン 10 個 + `llm_proposed` + 終端の `complex`)ありました。

そして、この trace を読んでいて一番効いたのが次の点でした。

> `one_side_change` / `non_overlapping` / `token_level_merge` / `refactoring_aware_merge`
> — この 4 つは **`hasBase: true`(共通祖先の情報)がないと評価すらされない**

git の既定のコンフリクトマーカー(`merge` スタイル)は ours と theirs しか書きません。共通祖先を出すには `merge.conflictStyle` を `diff3` / `zdiff3` にする必要があります。

既定設定のままだと、実パターン 10 個のうち 4 個が最初から使われません。信頼度スコアの内訳にも `baseAvailability: 0` と出ていて、それがスコアを押し下げています。

(なお `refactoring_aware_merge` は base があっても既定では無効で、base 付きで走らせると `RefMerge désactivé (options.refactoringAware.enabled !== true)` と出ます。`diff3` にして実際に増えるのは 3 個です。)

```json
"confidence": {
  "score": 58, "label": "medium",
  "dimensions": { "typeClassification": 68, "baseAvailability": 0, ... },
  "penalties": ["Sans base (diff2) — heuristique d'union (−22)"]
}
```

「base がないので union ヒューリスティックを使う、−22 点」。ドキュメントには「ours/theirs/base を返す」と書いてありますが、実際は git の設定次第で base が来ていません。

trace が読めること自体はかなり良くて、12 段のどこで落ちたかを理由つきで全部追えます。自動解決を信じるかどうかを、雰囲気ではなく根拠で決められました。

ただ、その根拠を見て分かったのは、既定の git 設定では分類能力を出し切れていないということでした。自動解決率が思ったより低いとき、コンフリクトが難しいのではなく `merge.conflictStyle` が `merge` のままなのかもしれません。`gitwand_explain_hunk` を叩いて `hasBase: false` が出ていたら、それが理由です。

## 罠: 解決率を上げようと `conflictStyle` を変えたら、壊れた CI が「解決済み」になった

前節のとおり、`merge.conflictStyle` を `diff3` / `zdiff3` にすれば base が渡り、使えるパターンが増えます。実際に切り替えると、自動解決は 3 件から 5 件に増えました。

```console
$ git config merge.conflictStyle zdiff3
$ gitwand resolve
✨ 5 conflict(s) auto-resolved out of 8
```

増えた 2 件の中身を見るまでは、これで片付いたと思っていました。

同じリポジトリ・同じマージを、3 つの `merge.conflictStyle` で回した結果です。

```console
style=merge : ci.yml内のcheckout行=2 / 未解決マーカー=1
style=diff3 : ci.yml内のcheckout行=2 / 未解決マーカー=0
style=zdiff3: ci.yml内のcheckout行=2 / 未解決マーカー=0
```

`merge`(既定)では ci.yml にマーカーが残っています。つまり人間に回された。`diff3` / `zdiff3` ではマーカーが消えて、解決済みの扱いになっています。

元の衝突はこうでした。

```yaml
    steps:
<<<<<<< HEAD
      - uses: actions/checkout@v5
||||||| 9f889c9
      - uses: actions/checkout@v4
=======
      - uses: actions/checkout@v4.2.2
>>>>>>> feature/api-v2
```

同じ 1 ステップのバージョン指定を、両ブランチが別々に変えただけです。どちらか選ぶ以外にありません。

これに `gitwand resolve` をかけると、こう出ます。

```console
  ✓ .github/workflows/ci.yml — 1/1 resolved
    L9 [complex] auto — Conflit complexe nécessitant une résolution manuelle.
      trace: Conflit complexe — toutes les heuristiques automatiques ont échoué.
```

**`[complex]`(= 手動解決が必要)と分類しておきながら、`auto` として適用し、`✓ 1/1 resolved` と報告しています。**

そして書き込まれたのがこれです。

```yaml
    steps:
      - uses: actions/checkout@v5
      - uses: actions/checkout@v4.2.2
      - uses: actions/setup-node@v4
```

checkout ステップが 2 回並びました。union されています。

しかもこれ、YAML としては完全に valid です。

```console
$ ruby -ryaml -e 'p YAML.load_file(".github/workflows/ci.yml")["jobs"]["typecheck"]["steps"].map{|s| s["uses"] || s["run"]}'
["actions/checkout@v5", "actions/checkout@v4.2.2", "actions/setup-node@v4", "npm ci", "npm run typecheck"]
```

構文チェックもコンフリクトマーカー検査も通ります。CI 自体も動きはします。v5 でチェックアウトした直後に v4.2.2 で上書きチェックアウトするので、余計な時間を使い、`fetch-depth` などの指定も後勝ちになるだけです。落ちてくれないので、気づく機会がありません。

念のため、分類器自身に聞き直しました。base がある状態でも判定は変わりません。

```
type: complex | hasBase: true | confidence: 60 medium
 - non_overlapping: false | 3-way LCS が重なりを検出 — 両ブランチが同じ行を変更
 - value_only_change: false | ours と theirs の差は volatile な値だけではない
 - complex: true | 自動パターンなし — 手動解決が必要
```

分類器のほうは「手動が必要」と正しく答えています。にもかかわらず `gitwand resolve` が union を書き込む。**分類器のミスではなく、resolve コマンド側の適用ロジックの問題**だと思います。base が取れている時だけ再現しました。

サイトにある `zero gambling with your code` は、少なくとも `conflictStyle = diff3` の環境では成立していないことになります。

### それでも使うなら、当面はこうするのが安全

- `merge.conflictStyle` は既定(`merge`)のままにする。解決率は下がりますが、解けないものは解けないと諦めてくれます
- `gitwand resolve` の後に `git diff --staged` を見る。自分はこれをやっていたので、上の union に気づけました
- CI に組み込むなら `--dry-run` か `--ci` で止めて、人間のレビューを挟む

v3.6.0 時点の話です。再現手順はスクリプト 1 本で回せるようにしてあるので、直ったかどうかは同じ手順で確認できます。

### GUI で引っかかったところ

**1. インラインの説明もフランス語**

マージエディタの中の説明文も `Conflit complexe nécessitant une résolution manuelle.` でした。**GUI で作業していると、ここが一番よく目に入ります**。

**2. 設定画面は英語とフランス語が混ざる**

`APPLICATION` は英語、`DÉPÔT`(リポジトリ)`IA & AGENTS`(AI & エージェント)`SYSTÈME`(システム)はフランス語で、同じ画面に 2 言語が並びます。英語表記のつもりで探していたため、**目的の項目を見つけるのに少し時間がかかりました**。

![GitWand の設定画面。左サイドバーに APPLICATION / DÉPÔT / IA & AGENTS / SYSTÈME という英語とフランス語の見出しが並ぶ](/images/eb3cf80133be2f/desktop-settings.png)

**3. リポジトリはフォルダピッカーからしか開けない**

`open -a GitWand <path>` でパスを渡せません(`Info.plist` に `CFBundleDocumentTypes` も URL スキームも未定義)。**必ず GUI のフォルダピッカーを通す**必要があります。ターミナルから `gitwand open .` のように開けると嬉しい。

**4. `--verbose` 相当の decision trace が GUI から見えない**

CLI と MCP では 12 段の分類ステップが全部見られるのに、**GUI では最終判定の 1 文だけ**です。GUI だけで作業していると、この情報にたどり着けませんでした。

GUI は、コンフリクトを 1 ファイルずつ目で見て潰していく分には合っていました。ただリポジトリ全体を一括で自動解決するボタンは見当たらず(`Actions` メニューにもありません)、判断根拠も 1 文しか出ません。結局、一括処理と根拠の確認は CLI、1 件ずつ手で確定させるのは GUI、という使い分けに落ち着きました。

## MCP サーバ: Claude Code から使う

ここが個人的に一番おいしかった部分です。

```bash
claude mcp add gitwand -- npx -y @gitwand/mcp
```

公開ツールは、ドキュメント記載の 5 個ではなく 7 個ありました。

| ツール | 何をするか |
|---|---|
| `gitwand_status` | 衝突ファイル一覧を構造化 JSON で返す |
| `gitwand_resolve_conflicts` | パターン自動解決。`policy` 指定可 |
| `gitwand_preview_merge` | 副作用なしで merge/rebase/cherry-pick を予測 |
| `gitwand_explain_hunk` | **12 段の decision trace を返す** |
| `gitwand_apply_resolution` | 任意の解決内容を書き込む |
| `gitwand_resolve_hunk` | **呼び出し元のエージェント自身に解決を依頼するプロンプトを返す** |
| `gitwand_resolve_hunk_llm` | LLM の提案を検証してから適用(スコア閾値つき) |

注目は `gitwand_resolve_hunk` です。説明文にこうあります。

> This tool does NOT call any external LLM — the agent that called the tool IS the LLM.

外部 API を呼ばず、base/ours/theirs を整形したプロンプトを返して、呼び出したエージェントに考えさせる作りです。API キーを用意せずに済み、Claude Code がそのリポジトリで何をしていたかの文脈をそのまま使えました。今回の検証で一番手応えがあったのはここです。

`gitwand_resolve_hunk_llm` の方も、LLM の出力をそのまま信じずに、マーカー残存チェックと JSON/YAML の構文チェックを通し、スコアが閾値(既定 80)未満なら書き込まないようになっています。提案がそのまま反映されないので、試すときの心理的な負担は軽かったです。

一方で、MCP の `gitwand_status` が返す数字も CLI とは一致しませんでした。

```json
{ "files": 6, "totalConflicts": 7, "autoResolvable": 0, "remaining": 7,
  "tierSummary": { "byTier": { "trivial": 4, "unresolved": 3 } } }
```

`autoResolvable` は 0、`byTier.trivial` は 4、CLI の `status` は 3、実際に `resolve` して解けるのも 3。同じ状態について、集計の取り方ごとに違う数字が並びます。エージェントがこの JSON だけを見て動くと、`autoResolvable: 0` を根拠に「自動解決できるものは無い」という前提で進んでしまいます。

なので MCP 経由で使うなら、集計値ではなく trace を読ませたほうが良さそうです。`gitwand_resolve_conflicts` を `dry_run: true` で走らせて実際の判定結果を取り、`gitwand_explain_hunk` で根拠を確認させる。残った complex なハンクは `gitwand_resolve_hunk` でエージェント自身に考えさせ、`gitwand_resolve_hunk_llm` の検証を通して書き込む。この順番なら、上の数字の食い違いは踏まずに済みます。

## 総評

エンジンそのものでは困らなかったのに、その周りで何度か足を取られた。これが触ってみた率直な感想です。

良かったところ:

- **解けないものを解かない**。両ブランチが別アルゴリズムで書き直した関数に手を出さなかった。自分がこの種のツールで一番気にしているのはここでした
- **decision trace が本物**。12 段の分類ステップを落ちた理由つきで全部読めるので、ツールの判断を自分で検証できた
- **適用前に中身が読める**。CLI の `--dry-run`、GUI の確認ダイアログ、どちらも押す前に結果を確認できた
- **軽い・速い・署名済み・テレメトリなし・MIT**。導入で引っかかる場面が無かった
- **MCP の `gitwand_resolve_hunk`**。API キーなしで、呼び出し元エージェントの文脈をそのまま使えた

引っかかったところ:

- **`conflictStyle` を `diff3`/`zdiff3` にすると、`complex` 判定のハンクに union を適用して「✓ resolved」と報告する**。壊れた CI 設定が静かに通る
- **既定設定では 10 パターン中 4 つが評価すらされない**。base が届いていないため
- **trace の文言と実際の動作がズレる**(「theirs を採用」と書いて ours を採用する等)
- **`preview` / CLI `status` / MCP `status` で数字が 3 通り**に割れる。件数を予測として使うことはできませんでした
- **説明文がフランス語**。CLI・GUI・MCP のいずれも、環境変数では英語に切り替えられなかった
- **シークレットスキャンは接続文字列内のパスワードを見逃す**

### なぜ見送ったか

一番効いたのは、**引っかかった 1 つ目と 2 つ目が噛み合ってしまうこと**でした。

- 既定設定(`merge`)なら安全に止まってくれる。ただし**7 件中 3 件しか解けない**
- `diff3` 系にすれば解ける数は増える(3 → 5 件)。**ただし増えた中に壊れた CI 設定が混ざる**

**安全側を選ぶと得られる時間が小さく、時間を取りに行くと黙って壊れる。** この二択のどちらを選んでも、結局 `git diff --staged` を全ハンク自分で読み直すことになります。そこまでやるなら、自分が削れると思っていた手間はほとんど削れていません。

もう 1 つ、リスクを管理する側の情報を信用しきれなかったのも大きいです。union を踏んでも「trace を読めば分かる」なら運用でカバーできますが、その trace は「theirs を採用」と書いて ours を採用し、件数は 0 / 3 / 4 と 3 通りに割れ、説明文は自分が読めない言語で出ます。気をつけて使うための足場が、いまは揃っていないと感じました。

チームに配ることを考えると、説明文が読めない点だけでも厳しいものがありました。

とはいえ、どれも設計そのものの話ではなく、まだ手が回っていないだけに見えます。再現手順は付録にスクリプト 1 本で置いてあるので、バージョンが上がったらまた同じものを回してみます。

- リポジトリ: <https://github.com/devlint/GitWand>

````bash
const WINDOW_MS = 60_000;
const LIMIT = 100;

const hits = new Map<string, number[]>();

export function isAllowed(key: string): boolean {
  const now = Date.now();
  const win = hits.get(key) ?? [];
  const fresh = win.filter((t) => now - t < WINDOW_MS);
  if (fresh.length >= LIMIT) {
    hits.set(key, fresh);
    return false;
  }
  fresh.push(now);
  hits.set(key, fresh);
  return true;
}
EOF

const CAPACITY = 20;
const REFILL_PER_SEC = 5;

const buckets = new Map<string, { tokens: number; last: number }>();

export function isAllowed(key: string): boolean {
  const now = Date.now();
  const b = buckets.get(key) ?? { tokens: CAPACITY, last: now };
  const refill = ((now - b.last) / 1000) * REFILL_PER_SEC;
  b.tokens = Math.min(CAPACITY, b.tokens + refill);
  b.last = now;
  if (b.tokens < 1) {
    buckets.set(key, b);
    return false;
  }
  b.tokens -= 1;
  buckets.set(key, b);
  return true;
}
EOF
````
