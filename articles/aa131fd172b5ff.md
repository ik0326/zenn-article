## 153 人のうち、対戦したのは 4 人

先日リリースした [写経Programming](https://shakyo-programming.dev) というオンライン対戦タイピングゲームに、最近 X で告知をしました。狙いどおりというか、想定以上に伸びて、**1 日で +97 人**。気づけば登録ユーザーは **153 人**になっていました。個人開発で 100 人を超えたのは初めてで、その日は素直にはしゃいでいました。

翌朝、運営者として一応 DynamoDB を覗いてみたんですよ。**そこで現実を見ました**。

```
shakyo-ratings 総レコード数: 153
うち wins/losses/draws のいずれかが > 0 の人: 4
```

153 人中、**1 度でも対戦した人は 4 人**。残り 149 人は、登録して、たぶん 1 人で写経して、対戦は試さずに帰っていったということです。**97.4 % の人が、私が一番見せたかった機能を一度も触っていない**。

このサービスの売りは「**1v1 のオンライン対戦 + Glicko-2 レーティング**」です。それが完全に機能していない。X で何人もの方が「面白そう」とリツイートしてくれて、登録までしてくれているのに、肝心の対戦が回らない。**しんどい**。

しんどいんですが、しんどがってる場合じゃないので、原因を分けて見ていきます。

## なぜ過疎るのか ― chicken-and-egg

データを見るまでもなく、原因は単純でした。

- 新規ユーザー A がキューに入る
- まわりに誰もいない
- A は数十秒待って諦めて離脱する
- 30 分後に B が来る
- A はもういない
- B も数十秒待って離脱する
- …

**キューには誰も残らないので、新規が来ても常に空のキューに迎えられる**。これがいわゆる **chicken-and-egg 問題**で、対戦ゲームではかなりよくあるやつです。ニワトリも卵もいない。先に並ぶ人が居ないと、後から来る人もマッチしない。

きつい点はもう一つあって、**対戦を 1 度も体験しないと、そのゲームが面白いかどうかも判断できない**ということです。「写経」だけならソロでも遊べますが、「対戦」のテンションは対戦してみないと分からない。**最初の 1 戦が起きないと、リテンションは作れない**。

データに戻ると、対戦経験のある 4 人は内訳がこうでした。

```
認証ユーザー: 12W / 2W / 15W
ゲストユーザー: 1W
```

15 戦してくれている人もいる一方で、**ゲスト 148 人のうち、対戦できたのはわずか 1 人**。「ゲストでとりあえず触ってみる人」のほぼ全員が、対戦を体験しないまま帰っている、というのが構造的にハッキリ見えました。

## 4 つの打開案を並べてみた

Claude Code と相談しながら、打開策を 4 つ並べました。

1. **ボット対戦**: キューに数十秒誰も来なければ、ボットを割り当てる
2. **ゴースト対戦**: 過去の他人のタイピングログを「相手」として再生する
3. **マッチ通知**: 誰かがキューに入ったら、登録ユーザーにメール/Push を飛ばす
4. **スケジュール対戦**: 「毎日 21:00 はラッシュアワーです」と告知して人を同期させる

それぞれ筋はあります。3 番の Push は時間軸の問題に直接効く一方で、PWA Push の実装コストがそこそこ重い。4 番は「告知だけでよくない?」と思いつつ、そもそも告知を見てくれる規模じゃない(私の X のフォロワー数を冷静に見ました)。

**1 番のボット対戦に決めました**。理由は 3 つ。

- 実装コストが最小。すでに「対戦相手をクライアント側でシミュレートする」MockDuelClient というのが残っていて、対戦画面を作っている初期にローカルで遊ぶ用に書いたものをほぼそのまま流用できる
- 「対戦が必ず成立する」状態を 100% 担保できる(他案はキューに人が来ない限界がある)
- 「人間相手が居なければ AI 相手で繋ぐ」という最近のオンラインゲームのデフォルトに合っている

ここから先、**ボットを入れる設計**を、特に面白かった 3 つに絞って書きます。

- SQS DelaySeconds で「30 秒タイマー」を AWS に丸投げする
- Glicko-2 の不確実性表現で、レート変動を **自然に** 縮める
- 戦績は対人と対 BOT を別カラムで持つ(誠実さの話)

## SQS DelaySeconds で「30 秒タイマー」を AWS に丸投げする

「キューに入って 30 秒経ってもまだ相手が来なければ、ボットを割り当てる」

これを愚直に実装しようとすると、定期実行の Lambda を立てて、キューを scan して、`joinedAt < now - 30s` のエントリを拾って…という cron 型になります。動きはするんですが、**30 秒に 1 回 Lambda が起動し続ける**コストと、最大遅延が 0〜30 秒で揺れるのが気持ち悪い。

**SQS の DelaySeconds**を使うと、これが一発で消えます。

`queue.join` を受けたタイミングで、通常の matcher 用 FIFO に 1 通積むのと一緒に、別の「ボット召集チェック」用 FIFO に **DelaySeconds=30** で 1 通積む。SQS が 30 秒持ったあとで配送してくれて、それを受けた matcher Lambda が「このユーザー、まだキューに居ますか?」をチェック。居れば bot 召集、居なければ no-op(= 既に人間と当たっている / 離脱した)。

```go
// lambda-ws (queue.join 受信時)
sqsClient.SendMessage(ctx, &sqs.SendMessageInput{
    QueueUrl:       aws.String(matcherQueueURL),
    MessageBody:    aws.String(bucket),
    MessageGroupId: aws.String(bucket),
})
sqsClient.SendMessage(ctx, &sqs.SendMessageInput{
    QueueUrl:       aws.String(botCheckQueueURL),
    MessageBody:    aws.String(`{"userId":"...","bucket":"b15","joinedAt":...}`),
    MessageGroupId: aws.String(userID),
    DelaySeconds:   aws.Int32(30),
})
```

これだけで「30 秒タイマー」が完成します。**自分でタイマーを持たなくていい。SQS が持ってくれる**。

おまけで、「待ちたくないユーザー向けの即 Bot マッチ」も用意しました。`queue.join_bot` という別 action を切って、こちらは `DelaySeconds=2` で同じキューに積む。2 秒猶予を入れているのは、**人間優先のため**です。即 Bot を選んだ user も、たまたま同時に人間が居れば人間と当ててあげたい。matcher.fifo を先に走らせて、2 秒後にまだキューに残っていれば bot を召集する、という順序にしました。

| 操作 | t=0 人間あり | t=0〜30s 人間来る | 両方なし |
|---|---|---|---|
| `queue.join` | 即 人間 | 30s 以内なら人間、超えたら bot | 30s 後 bot |
| `queue.join_bot` | 即 人間 | 2s 以内なら人間、超えたら bot | 2s 後 bot |

UI 上はこんな感じで、マッチング画面のど真ん中に「BOT と今すぐ対戦」というボタンを置いています。

![マッチング画面: BOT と今すぐ対戦ボタン](/images/aa131fd172b5ff/matching-screen-bot-button.png)

「ボット入れて即マッチ」って言いつつ、**人間が居ればこっそり人間と当てる**。ちょっと裏切ってる感じもありますが、体験としてはこちらの方が嬉しいだろう、というのが今の判断です。

## Glicko-2 の不確実性表現で、レート変動を自然に縮める

ボット戦でもレーティングは動かしたい、けど対人と同じ重みにはしたくない、というのが今回の悩みでした。「人間相手で勝ったときと、ボット相手で勝ったときで、+30 点ずつ入る」のは、**対戦してくれた人間の方に申し訳ない**。

最初は「ボット戦の delta を 0.3 倍に縮める」みたいな ad-hoc な縮め方を考えました。シンプルで分かりやすい一方で、**Glicko-2 の数学に外側からハサミを入れる感じ**で、後で追っかけたときに「なぜここで 0.3?」を説明できる気がしない。

ここで、Glicko-2 の良いところを思い出しました。Glicko-2 は **rating** だけじゃなく **RD (Rating Deviation)** という「その人の実力推定がどれくらい不確かか」という値を持っています。RD が大きい相手と対戦すると、自分のレートは **大きくは動かない**。「実力が不確かな相手から得た情報は、信頼度が低い」というのを、アルゴリズム自体が組み込んでいるわけです。

これを使います。**ボット側の opponent record を、RD=350(初期値・最大値)で渡す**。

```go
// applyRatingDeltaBot
newUser := rating.Update(
    rating.Rating{Rating: user.Rating, RD: user.RD, Volatility: user.Volatility},
    []rating.Opponent{{
        Rating:  bot.Rating,
        RD:      350,     // ← ここが今回の核
        Outcome: outcome,
    }},
)
```

ボット自身は内部に Glicko-2 状態を持っていて、対戦履歴で動的に rating を更新しているのですが、**user 側に「opponent」として渡すときは、常に RD=350 で渡す**。これによって user 側の rating は自然に小さく動きます。

実際に Go 実装を書いて測ってみました。

- 通常対戦(1500/RD=100 vs 1500/RD=100、勝ち): **+26 点**
- ボット対戦(1500/RD=100 vs 1500/RD=350、勝ち): **+19 点**
- 比率: **0.728**(約 27 % 縮小)

設計段階の手計算では「+27 → +8 くらい」と楽観的に見積もっていたんですが、実装してテストを書いて流したら **+26 → +19** でした。**けっこう過大評価していたわけです**。

これは Glicko-2 の g(φ) 関数の数学的な上限(理論値 ≈ 0.7)に律速されている結果で、RD=350 はもう Glicko-2 の取りうる最大値なので、これ以上 RD で縮めるのは無理。「もっと縮めたければ、Glicko-2 の外側で `delta *= 0.5` のような scale factor を掛けるハイブリッド方式に切り替える必要がある」というのが、実装してみて初めて見えた境界線でした。

ただ、**Glicko-2 の意味論にそのまま乗っている**ので、後で読み返したときに「なぜここで RD=350?」が「ボットの実力は不確実な扱いなので」で説明できる。ad-hoc な係数を掛けるより、**未来の自分への説明コストが安い**。今回は約 27 % の縮小で「対人より明らかに少ない」が言えるなら、まずはここで様子見、と決めました。**過剰設計しない**判断です。

> Glickman 本人の論文(*[Example of the Glicko-2 system](https://www.glicko.net/glicko/glicko2.pdf)*)を読むと、RD=350 は「まだ一度も対戦していない初期状態のプレイヤー」と同じ値です。「ボット = 何度対戦しても実力が安定的に推定できない相手」と扱うことで、シミュレーションの不確実性を user に押し付けない、という意味を持たせています。

## 戦績は対人と対 BOT を別カラムで

これは技術というより、**誠実さ**の話です。

`shakyo-ratings` テーブルには `wins / losses / draws` というカラムが既に並んでいます。ここにそのままボット戦の結果を混ぜると、ランキング画面で「**この人 30 勝してるすごい**」となったとき、その 30 勝が全部 BOT 戦かもしれない。それは違うな、と。

なので **botWins / botLosses / botDraws** という別カラムを増やします。スキーマレスな DynamoDB なので、既存 153 件に対する migration は要らない(欠損 = 0 として読む)。UI の方も、結果画面と戦績画面で「対人 12W / 対 BOT 5W」と並べて見せます。

レーティングの方は混ぜます。Glicko-2 は RD=350 トリックで自然に縮んでいるので、ボット戦込みで一本化して問題ない。**戦績は別、レーティングは一本**。この使い分けがちょうど良いところに落ちた感覚があります。

## 「ボットです」と書く

最後にもう一つ、製品の判断として悩んだのが「**ボットだと正直に伝えるか、人間っぽく見せるか**」でした。

人間っぽく見せるパスは、対戦の臨場感は最大化されます。一方で、後で「BOT_*** って実はあの時のあれ?」みたいにバレた瞬間の信頼コストはかなり重い。**個人開発で一度信頼を落とすと、取り戻す手段が無い**。

選んだのは **明示開示**です。

- 名前を `BOT_SwiftFalcon#0001` のように `BOT_` prefix 固定
- マッチング画面に「**BOT**」バッジを常時表示
- 結果画面でも「BOT 戦」と明示

副次的に良かったのは、**レート変動を縮める理由がそのまま「ボットだから」で説明できる**ことです。「対人と対 BOT で動く量が違うのは、ボットだから」。開示しているからこそ言える設計です。隠していたら、「なんで動かないの?」に答えられない。

そして何より、**この記事が書けるようになる**。「ボットを入れました、こうやって縮めました」とコードと数式を一緒に書ける状態でリリースできる方が、私には合っていました。

## 実装はこれから。結果はまた書きます

ここまで読んでくれた方ならお気づきだと思いますが、この記事を書いている時点では、**ボット対戦はまだ実装していません**。Claude Code とブレストして設計を spec に落として、コミットしたところです。これから 3 リポ(api / infra / web)を順に書いていきます。

リリースしたら、**実際の数字を計測**して、続編を書くつもりです。

- ボット対戦の導入で、登録ユーザーのうち対戦経験者の比率は何%まで上がったか
- 「即 Bot マッチ」と「30s 待ち」の選択割合はどうなったか
- 対人マッチが復活した瞬間があるか(= ボット戦で滞留した人が、後で来た新規と人間マッチを成立させる事例)

正直に出します。**増えなかったら増えなかったで、なぜ効かなかったかを書きます**。失敗の話の方が、他の個人開発者の役には立つはずなので。
